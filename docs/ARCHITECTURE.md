## 0. 요약

- **앱이 곧 제품입니다.** 기록, 지도, 통계, 백업은 모두 기기 안에서 끝납니다.
- **저장은 둘뿐입니다.** 쓰기 가능한 `user.sqlite` 하나와, 통째로 교체하는 읽기 전용 **데이터 팩**(master, names, rail, rail-osm, base, 글리프)입니다.
- **사용자가 입력한 값이 원본이고, 나머지는 전부 입력과 데이터 팩에서 다시 계산합니다.**
- **프론트엔드는 Flutter**이고 지도는 MapLibre 네이티브입니다. 규칙은 순수 Dart 패키지 `noriori_core`에 둡니다.
- **서버는 v1.0 범위 밖입니다.** 나중에 붙일 수 있게 최소한만 준비합니다 (§5).

```
 ┌───────────── 데이터 백엔드 (빌드 타임) ─────────────┐
 │ data/source → compile.py → master, names            │
 │             → gen_tiles.py → rail, rail-osm.pmtiles │
 └───────────────────────┬─────────────────────────────┘
                         │ 앱에 포함. 내려받기는 P1
                         ▼
 ┌──────────────────── 앱 (Flutter) ───────────────────┐
 │ UI 격리    지도 · 기록(역 선택기) · 통계 · 설정     │
 │            선로망 그래프, 해석 (작업 격리는 §0.2)   │
 │ core       날짜, 경로, 상태표, 완주 계산 (순수)     │
 │ store      user.sqlite + 데이터 팩(읽기 전용)       │
 └─────────────────────────────────────────────────────┘
```

### 0.1 불변식

깨지면 제품이 실패하는 것들입니다. 모든 설계와 시험은 이것을 지키기 위해 있습니다.

| 번호 | 불변식 |
|---|---|
| 1 | 사용자가 지우지 않은 기록은 업데이트, 데이터 교체, 복원, 강제 종료 뒤에도 남습니다 |
| 2 | 해석할 수 없게 된 기록도 버리지 않고 `확인 필요`로 보여 줍니다 |
| 3 | 완주율은 유효 기록, 데이터 팩, 기준, 승계 설정만으로 정해집니다. 분자는 분모의 부분집합이고, 전 구간을 탔을 때만 100%입니다 |
| 4 | 한 세션은 데이터 팩 하나로 동작합니다 |
| 5 | 원본과 캐시는 어긋나지 않습니다 |
| 6 | 1인이 끝까지 유지할 수 있습니다 |

**복잡도 규칙**: 평범한 CRUD를 넘는 메커니즘은 어느 불변식 때문에 필요한지 대지 못하면 넣지 않습니다. "오래 걸릴 것 같다"는 측정한 뒤에만 근거가 됩니다.

### 0.2 측정으로 정한 것 (2026-11-01, 이 맥의 파이썬과 SQLite. 폰 측정이 아닙니다)

| 질문 | 실측 | 결정 |
|---|---|---|
| 전체 재해석이 오래 걸리나 | 그래프 적재 0.15초. 기록 5,000건 펼치기 0.29초 + 쓰기 0.08초, 2만 건 1.19초 + 0.31초 | 배경 빌드 불필요. 시작할 때 한 번에 |
| 통계 캐시가 필요한가 | 기록 2만 건에서 탄 단위 조회 23.6ms, 3기준 판정 19ms. 복합 인덱스 기준 | 캐시 없음. 판정은 순수 함수 |
| 지도용 탄 구간 집합 | 5,000건 3.0ms, 2만 건 9.5ms | 캐시 없이 SQL |
| 캐시가 파일을 키우나 | 5,000건(25구간) 11.9MB, 2만 건 47.6MB. 문자열 키 기준 | 한 파일로 충분. 정수 키로 더 줄임 |

**실기기 측정** (2026-11-02. 중급 Android 실기기(Android 12), 프로파일 빌드, 기록 없음. 3회)

| 항목 | 실측 | 판단 |
|---|---|---|
| 재시작 첫 화면 | 537~559ms | 예산 1.5초 안 |
| 재시작 지도 준비 (`StartReady`까지) | 846~876ms | 같음. 이 가운데 선로망 읽기 668~696ms, 색인 29~37ms |
| 첫 실행 (팩 복사 포함) | 2.49초 | 설치 뒤 한 번 |

선로망 읽기는 DB 격리에서 돌고 그동안 화면은 시작 화면이므로 **작업 격리를 아직 만들지 않습니다.** 복잡도 규칙대로 기록이 많을 때 재서 예산을 넘으면 넣습니다. 60fps는 아직 재지 않았습니다. 저장 반영 시간은 §2.6에 있습니다.

## 1. 저장소 구조

단일 저장소이고 Dart는 pub workspace로 묶습니다.

```
noriori/
├─ apps/noriori/            Flutter 앱
├─ packages/
│  ├─ noriori_core/         순수 Dart. 규칙과 타입. I/O와 Flutter 금지
│  └─ noriori_store/        drift. DB, 쿼리, 변경 적용, 데이터 팩 선택
├─ tools/                   데이터 파이프라인과 검사. tools/dev는 로컬 점검용
├─ data/                    원본(source), 손 보정(overrides), 원천(imports, git 제외)
├─ build/                   데이터 산출물 (git 제외)
├─ docs/                    명세와 spec-trace(구현 상태)
└─ .github/workflows/
```

**의존 방향**: `apps → store → core`. 역방향 import, core의 I/O, 기능끼리의 직접 import, 화면의 저장소 접근은 `tools/check_boundaries.py`가 CI에서 막습니다.

## 2. 프론트엔드

### 2.1 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| UI | Flutter stable (로컬 3.47.1) | 한 코드로 Android, iOS. 웹뷰 없음 |
| 지도 | `maplibre_gl` + 로컬 PMTiles | 네이티브 렌더링 |
| DB | `drift` + SQLite | 타입 있는 쿼리, 백그라운드 연결, 마이그레이션 |
| 상태 | Riverpod | 의존을 화면과 분리, 테스트에서 교체 쉬움 |
| 라우팅 | `go_router` | 탭별 스택 유지 |
| 다국어 | `slang` | 키를 컴파일 시 검사 |
| 차트 | 자체 위젯 | 패키지를 쓰지 않음. `years_screen`, `activity_screen` |

버전은 `pubspec.lock`에 고정하고, 지도 패키지를 올릴 때마다 지도 벤치를 다시 돌립니다.

### 2.2 계층과 실행 위치

| 계층 | 위치 | 하는 일 | 하면 안 되는 일 |
|---|---|---|---|
| 화면 | `features/*/ui` (기능 폴더 바로 아래 파일 포함) | 그리기, 입력 전달 | SQL, 규칙 판단, 저장소 import |
| 컨트롤러 | `features/*/controller` | 화면 상태를 불변 객체로 관리, 여러 단계 묶기 | 위젯 참조 |
| 플랫폼 어댑터 | `features/*/platform` | 폴더 선택, 파일 고르기 같은 채널 호출 | 화면 상태 소유 |
| 앱 | `app/` | 라우터, 공용 provider(`session_providers.dart`), 테마, 시작 절차 | |
| 공용 위젯 | `app/widgets` | 여러 기능이 쓰는 위젯 | 기능, 저장소 import |
| core | `noriori_core` | 입력 값을 받아 결과를 돌려주는 순수 함수 | I/O, 비동기 |
| store | `noriori_store` | 쿼리와 트랜잭션 | 규칙 판단 |

| 실행 위치 | 맡는 일 |
|---|---|
| UI 격리 | 위젯, 행 높이 측정 (`TextPainter`는 여기서만 씀), 탑승일 변경 시 상태표 재적용. 선로망 `Network`를 메모리에 들고 경로 펼치기, 해석, 통계 계산 |
| 작업 격리 | 아직 없음. 기록이 많을 때 재서 예산을 넘으면 `Network`, 재해석, CSV, 백업을 옮김 (§0.2) |
| drift 연결 | 쓰기 1개 + 읽기 풀. 시작 때 선로망 읽기 |

core는 저장소 인터페이스를 부르지 않습니다. store가 값을 읽어 넘기고 core는 계산만 합니다. 그래서 시나리오 시험이 DB 없이도 돕니다.

기능 폴더는 다섯입니다.

| 폴더 | 맡는 화면 |
|---|---|
| `map` | 지도 홈 |
| `record` | 기록 탭, 역 선택기, 노선 상세, 검색, 운행 계통 입력, 여정, 여러 노선 한 번에 기록, 지도 위 시트 |
| `stats` | 통계, 수집, 남은 구간, 연도별, 활동, 방문 역 |
| `settings` | 설정, 데이터 출처 |
| `data` | 백업, 복원, CSV, 삭제한 기록, 변경 소식, 시작이 막혔을 때의 화면 |

기능끼리 직접 import하지 않고 라우트와 공용 provider로만 만납니다. 지도와 기록 시트는 앱(`app/router.dart`)이 잇습니다. 경계는 `tools/check_boundaries.py`가 검사합니다.

### 2.4 상태 관리

- 루트 provider는 `sessionProvider`(`AppSession`)이고 값은 시작 때 고른 데이터 팩과 연결입니다. 선로망은 `networkProvider`(`Network`)입니다. **한 세션 안에서는 바뀌지 않습니다** (§3.6). 그래서 화면에는 팩 교체를 처리하는 코드가 없습니다.
- 사용자 기록은 drift `watch`로 흐르되, 지도·통계 쪽은 묶어서 한 번만 다시 계산합니다.
- **입력 상태는 `recordSessionProvider`(`RecordSessionController`, `RecordSessionState`) 하나가 소유합니다.** 분기 줄을 탭해 다른 노선으로 넘어가도 살아 있어야 하고(DESIGN §8), 5초 되돌리기도 앞 노선 선택을 복원해야 합니다. 화면별 `autoDispose` 상태로는 담을 수 없습니다.
- 세션 안의 선택은 `from(route, seq, node)`, `to(route, seq, node)`입니다. 계통 칩을 바꿔도 출발역을 유지하고, 운행 계통 입력이면 `serviceId`를 듭니다.
- 설정은 `setting` 테이블이 원본이고 provider는 그 캐시입니다.

### 2.5 역 선택기

東海道本線은 세로 10,000dp가 넘고, 탑승일을 바꾸면 즉시 다시 그려야 합니다.

1. UI 격리의 `SelectorBuilder(network).build(계통, 탑승일, links)`가 메모리의 `Network`에서 `List<SelectorRow>`를 만듭니다. DB를 다시 읽지 않습니다. 탑승일을 바꾸면 이 단계만 돕니다.
2. 행 높이는 UI 격리에서 `TextPainter`로 잽니다. 계통별 스냅숏과 (문자열, 글자 크기, 폭)별 행 높이 캐시는 東海道本線 벤치로 재 보고 예산을 넘으면 넣습니다 (§8).
3. 화면은 지연 목록이고 행마다 `CustomPainter`입니다. 탭하면 범위 안의 행만 다시 그립니다.

행을 그리는 입력은 전부 불변 값이므로 골든 이미지로 표시 규칙을 고정합니다.

## 3. 로컬 코어

### 3.1 저장 구조

```
앱 지원 폴더/
├─ user.sqlite          원본과 캐시                 OS 백업 포함 (-wal 포함)
├─ quarantine/          손상된 user.sqlite 보존     OS 백업 제외
└─ datasets/            데이터 팩                   OS 백업 제외
   └─ <판>/             팩 파일 (§4.5, 불변). 예: 2027-03-20.2/
앱 자산/                앱에 든 데이터 팩 (assets/pack, tools/sync_pack.sh가 복사)
```

| 규칙 | 내용 |
|---|---|
| 쓰는 곳 하나 | 모든 변경은 `RecordStore.apply(change)`를 지납니다. 원본 행과 그 기록의 캐시를 **한 트랜잭션**에 씁니다. 그래서 원본과 캐시를 맞추는 절차가 따로 없습니다 |
| 캐시 키 | `cache_state(edition, app_build)` 한 행입니다. 시작할 때 현재 값과 다르면 캐시를 전부 다시 만듭니다 (§3.6). 앱 빌드 번호를 쓰므로 규칙을 고치고 올리는 것을 잊을 상수가 없습니다 |
| 통계 캐시 없음 | SQL은 탄 단위별 최소 `effective_hi`만 주고, 판정은 `scoreTable`(`score/scorer.dart`) 하나가 합니다. 분모 단위는 메모리의 `Network`에 있습니다 (§0.2) |
| 행 하나의 실패 | 앱이 계산하지 못한 기록은 `ride_cache`에 `error`로 적고 나머지는 계속합니다 |
| 공간 부족 | 저장 트랜잭션이 통째로 실패합니다. 화면에 알리고 입력 내용을 유지해 다시 저장할 수 있게 합니다. 조용히 빠지는 기록이 없습니다 |
| 삭제 | 삭제 표시(`deleted_at`)입니다. 삭제된 기록의 캐시 행은 지웁니다 |

그 밖의 규칙:
- **판 폴더는 불변입니다.** 파일을 덮어쓰지 않습니다.
- 경로는 앱 지원 폴더 기준 상대 경로로만 다룹니다. iOS는 업데이트 때 절대 경로가 바뀝니다.
- 해시는 내려받을 때와 첫 복사 때만 검사합니다. 시작할 때는 파일 크기와 SQLite 헤더만 봅니다.
- 연결마다 데이터 팩의 두 파일을 `mode=ro&immutable=1`로 ATTACH합니다. Dart VM, iOS 시뮬레이터, Android 에뮬레이터에서 URI ATTACH, 쓰기 차단, FTS5, 격리 간 변경 알림을 확인했습니다. drift 기본 열기는 `uri: true`가 없어 ATTACH가 실패하므로 `Sqlite3` 래퍼로 명시합니다.
- 앱 코드는 `node`가 아니라 `node_public`을 읽습니다. 호환판 CSV의 `export_name`만 예외이고, 그 쿼리는 내보내기 파일에 격리합니다.
- 앱이 백그라운드로 갈 때 `user.sqlite`를 체크포인트합니다.
- 쓰기는 사용자의 입력이므로 `synchronous=FULL`입니다.
- 시작할 때 `user.sqlite`를 들여다보는 연결은 읽기 전용입니다. 쓰기로 열면 손상된 파일을 닫으면서 SQLite가 `-wal`을 지웁니다.

### 3.4 변경 처리

**모든 변경은 `Change` 하나입니다.** 저장, 수정, 삭제, 구간 탭, 일괄 삭제, CSV 가져오기, 복원 모두 같습니다.

해석 순서. 저장과 재해석이 **같은 순수 함수**입니다 (기준: `tools/appsim.py`의 `record`):

1. `date_input`이 원본입니다. `date`는 계산 값입니다.
2. 범위의 하한이 기준일(1950-01-01, `floorDate`)보다 이르면 기록 범위 밖이므로 날짜 없음으로 칩니다. 화면에 설명하지 않습니다.
3. 그 날짜로 펼칩니다. 범위 날짜는 영업 기간과 겹치면 탈 수 있습니다. 그날 그 구간을 탈 수 없으면(폐지 뒤, 개업 전, 운휴, 정차하지 않는 역) 경우마다 다르게 처리합니다 (사용자 결정, 2026-11-04).
   - 저장, 기존 기록의 날짜 수정: 경고를 띄우고 저장하지 않습니다. 원래 값을 유지합니다. 조용히 날짜 모름으로 바꾸지 않습니다.
   - CSV 가져오기: 묻지 않고 날짜 없이 펼쳐 날짜 모름으로 넣습니다. `date_input`에는 파일의 날짜를 그대로 두고, 가져오기 결과에 기준일 이전 날짜의 행과 합쳐 `날짜 모름으로 넣은 행 n건`만 보여 줍니다. 기준일은 말하지 않습니다.
   - 재해석(판이 바뀐 뒤): 묻지 않고 날짜 없이 펼쳐 캐시만 날짜 모름이 됩니다. 원본은 그대로입니다.
   날짜 없이도 경로가 없으면 `invalid`입니다.
4. 경로가 둘 이상이면 저장할 때 묻습니다. 범위 날짜가 이설에 걸친 경우도 같습니다. 재해석에서는 묻지 않고 `needs_input`입니다.
5. `RideInterpreter`가 그날의 노선과 계통을 맞춥니다.
6. 같은 함수가 유효 범위를 구합니다. 비면(범위 날짜에서 leg들의 영업 기간이 서로 겹치지 않는 경우) 탈 수 있는 날이 없는 것이므로 3번과 같이 나눕니다. 저장과 날짜 수정은 경고하고 저장하지 않습니다. CSV 가져오기와 재해석은 날짜 없이 5번부터 다시 합니다.

저장은 그 결과를 원본과 함께 한 트랜잭션에 씁니다. 재해석은 캐시만 씁니다. 노선이나 계통이 바뀌어도 원본은 그대로이고, **집계와 표시는 캐시의 `line_id`, `route_id`를 씁니다.** 폐지일이 정정되면 `date_input`에서 날짜가 되살아납니다. 순환의 한 바퀴는 `from_node == to_node`에 `direction`이 있는 leg입니다.

사용자 수정은 `updated_at`을 바꿉니다. 삭제와 되살리기도 같습니다. 값은 `max(현재 시각, 그 행의 이전 값 + 1)`이라 기기 시계가 돌아가도 그 행에서는 앞으로만 갑니다. 날짜를 고치면 `resolve_as_of`, `resolve_unknown`을 지우고 다시 펼치며, 필요하면 다시 묻습니다. 하루로 정해진 날짜는 `resolve_as_of`보다 앞섭니다.

**구간 끄기는 기록을 고치는 것입니다.** 별도 개체가 없습니다.
- `cutSection(ride, network, offUnits)`은 기록의 경로에서 그 집계 단위를 뺀 조각을 돌려주는 순수 함수입니다. 조각마다 legs를 다시 나눕니다. 범위 지정도 같은 함수이고, 기록이 그 구간을 두 번 지나면 두 곳 모두 잘립니다. 조각을 다시 펼쳐 경로나 날짜가 달라지면 기록을 건드리지 않고 멈춥니다.
- 조각이 하나면 그 기록을 고칩니다. 둘이면 앞 조각이 원래 ID를 갖고 뒤 조각은 새 ID를 받습니다. 조각이 없으면 삭제 표시입니다.
- 조각끼리 다른 것은 `id`, `updated_at`, legs, 잘린 끝 표시뿐입니다. `created_at`, `import_source`를 포함한 나머지 열은 전부 복사합니다. `transfer_nodes`는 그 조각의 경로 안에 있는 것만 남깁니다.
- 잘려서 생긴 끝은 승하차가 아니라 통과입니다. 끈 구간에 닿은 쪽의 끝이 곧 잘린 끝입니다.
- 그 구간을 덮는 기록이 여럿이면 전부 고치고 영향 건수를 표시합니다. "덮는 기록"은 화면의 집계 단위 기준이고 `ride_edge`로 찾습니다.
- 끈 구간 자체도 같은 규칙으로 복사한 **삭제 표시된 조각**으로 남습니다. `삭제한 기록`에서 되살릴 수 있습니다.
- 켜기는 그 구간과 정확히 같은 삭제 조각이 있으면 가장 최근 하나만 되살리고, 없으면 그 구간만 있는 날짜 없는 새 기록을 만듭니다.
- 숨은 노드에서 끊어야 하면 안내만 합니다.

**되돌리기**는 메모리의 `Change.before`로 **새 변경**을 만들어 `apply`를 지납니다. 그 사이 자동 백업이 나갔어도 복원에서 되돌린 결과가 이깁니다. 되돌림으로 없어지는 새 행은 삭제 표시입니다. 5초가 지나면 `Change.before`는 버리고, 그 뒤의 복구는 `삭제한 기록` 화면입니다.

### 3.6 데이터 팩 선택과 재해석

**활성 판을 저장하지 않습니다.** 시작할 때마다 폴더를 보고 고릅니다.

```
[콜드 스타트]
 0. user.sqlite 열기 → user_version 확인 → 필요하면 VACUUM INTO 사본 뒤 마이그레이션
    사본이나 마이그레이션이 실패하면 파일을 그대로 두고 재시도 화면으로. 다음 시작에 다시 시도
    파일이 손상되어 열 수 없으면 quarantine/으로 옮기고 복원 전용 화면으로
    quarantine/에 파일이 있으면 사용자가 복원을 마치고 화면을 닫을 때까지 빈 DB로 넘어가지 않음
 1. .tmp-* 삭제
 2. 앱 자산 팩과 datasets/의 팩 중 앱이 지원하는 스키마에서 가장 높은 판을 고름
    판 순서는 §4.5 (compareEditions). 같은 판이면 이미 폴더에 있는 쪽
    자산 팩이 뽑혔는데 폴더에 없으면 .tmp로 복사한 뒤 이름 변경
 3. 파일 크기와 헤더 확인. 깨졌으면 그 폴더를 지우고 2번으로
 4. cache_state가 (판, 앱 빌드)와 다르면 전체 재해석. 한 트랜잭션, 진행 표시, 변경 내역 저장
 5. 화면
 6. 쓰지 않는 팩 폴더 삭제
```

- 모든 단계는 다시 돌아도 같은 결과입니다. 어느 단계에서 죽어도 다음 시작이 처음부터 합니다. 마이그레이션과 4번은 트랜잭션이라 끝나지 않으면 없던 일입니다. 그래서 마이그레이션 버그는 고침 릴리스가 같은 파일을 다시 올리면 풀립니다. `PRAGMA user_version`도 같은 트랜잭션에서 씁니다 (drift 기본 동작은 따로 씀). 사본은 임시 이름으로 만들고, 남은 임시 파일은 먼저 지웁니다.
- 복원 전용 화면은 JSON 복원과 격리 파일 내보내기를 함께 제공합니다.
- 세션 중에는 교체가 없습니다. 내려받기는 폴더에 넣는 것까지만 하고, 적용은 다음 시작입니다.
- 앱 업데이트로 규칙이나 팩이 바뀌어도 같은 길입니다. OS 복원으로 폴더가 없어도 같은 길입니다.
- **판은 앞으로만 갑니다.** 잘못 낸 판은 번호를 올린 고침 판으로 덮습니다. 철회와 이전 판 보관이 없습니다.
- 재해석 결과가 같으면 조용히 넘기고, 다르면 변경 내역을 보여 줍니다. 비교는 옛 `ride_cache`로 하므로 이 표의 비교 열(상태, 날짜, km)은 바꾸지 않습니다. 사용자 스키마 변경이 캐시를 건드릴 때는 판 변경을 같은 릴리스에 넣지 않습니다.

**데이터 내려받기 (P1)**: `manifest.json`과 `.sig`를 받아 서명 확인 → 스키마와 최소 앱 버전 확인 → `.tmp-<판>/`에 내려받기 → 해시 확인 → 이름 변경. 공간이 모자라면 시작하지 않습니다. 중단되면 다음에 처음부터 받습니다. 사용자가 누를 때만 받습니다.

### 3.7 백업과 복원

| 항목 | 방식 |
|---|---|
| **자동 백업 파일 (P0)** | 사용자가 고른 위치(Android 저장소 접근, iOS 파일 앱 폴더)에 변경이 있으면 앱이 백그라운드로 갈 때 JSON을 씀. 새 파일을 다시 읽어 확인한 뒤에만 회전. 읽을 수 있는 파일 3개를 두고, 옛 파일은 **읽어서 병합해도 아무것도 안 바뀔 때만** 지움. 재설치나 OS 복원 뒤에는 옛 파일이 더 새로운 값을 갖고 있으므로 지우지 않고 병합 복원을 물음. 읽지 못한 파일(구름 자리표시자, 더 새로운 스키마, 깨진 파일)은 지우지 않고 지도 홈에 표시. 설정에 `마지막 백업 시각`, 오래됐거나 실패하면 지도 홈에 표시 |
| 수동 백업 | 같은 JSON 파일을 사용자가 고른 곳으로 내보냄. 사진과 ZIP 묶음은 v1.0 밖 (DESIGN v0.45) |
| 복원 | **병합만 있습니다.** 같은 ID는 `updated_at`이 늦은 쪽, 같으면 로컬, 없는 ID는 추가. 옛 파일을 잘못 골라도 새 기록이 사라지지 않습니다. 예외는 하나입니다: 로컬 행이 파일보다 옛것이고(OS 복원, 일부 복원) 시계가 그 사본보다 뒤처진 채 그 행을 고친 뒤 병합하면 그 행의 마지막 입력 1건이 집니다. 네 조건이 겹쳐야 하므로 받아들입니다. `user.sqlite`를 열 수 없을 때도 복원 전용 화면에서 같은 절차로 합니다 |
| 백업 형식 | 최상위에 `kind`(`noriori-backup`), `format`, `user_version`, `edition`, `app_build`, `exported_at`, `tables`. 파일은 이름이 아니라 이 머리말로 알아봅니다. 파일의 `user_version`이 앱보다 높으면 복원을 거부하고 앱 갱신을 안내. 더 낮으면 앱의 마이그레이션 순서대로 올려서 병합. 첫 공개 뒤에는 나간 파일을 고칠 수 없으므로 이 머리말은 고정 |
| 변경 판단 | 폴더에 같은 내용(행 순서 무시)의 파일이 있으면 쓰지 않고 실패로 치지 않음. 시각은 그 파일의 값을 씀. 빈 DB는 쓰지 않음: 재설치 직후일 수 있고 복원을 묻는 것이 먼저임 |
| 안내 | 지도 홈 안내의 우선순위는 병합 필요 > 실패 > 권한 소실 > 읽지 못한 파일 > 오래됨 > 폴더 없음. 바뀐 기록이 7일 넘게 백업되지 않으면 오래됨. 바뀐 것이 없으면 시간이 지나도 알리지 않음 (`backupNotice`) |
| 옛 파일 | 표 단위 `backupSteps`로 앱 버전까지 올린 뒤 병합. 단계가 없으면 읽지 못한 파일. 스키마를 올릴 때 마이그레이션과 함께 추가함 |
| 복원 전용 화면 | 격리를 둔 채 빈 `user.sqlite`와 팩으로 세션을 열어 병합함. 탭이 없음. 화면을 닫으면 격리 파일을 `quarantine/closed/`로 옮기고 지우지 않음. 닫기 전에 죽으면 복원한 행을 지키고 다시 이 화면. 같은 시각에 다시 격리해도 먼저 격리한 파일을 덮어쓰지 않음 |
| 마이그레이션 사본 | 마지막 마이그레이션의 사본 하나만 둠. 그 앞의 사본은 지금 DB가 대신함 |
| 공간 부족 | 팩 복사, 사본, 마이그레이션, 재해석의 ENOSPC·EDQUOT·SQLITE_FULL은 파일을 그대로 두고 공간 안내와 다시 시도 |
| Android 쓰기 | 임시 이름으로 쓰고 이름을 바꿈. 쓰는 도중 죽어도 회전이 영영 지우지 못하는 조각이 남지 않음. 이름 변경을 못 하는 저장소는 바로 씀 |
| 앱 안 위치 | 앱을 지우면 사라지는 폴더는 저장하지 않고 다른 폴더를 고르게 함 |
| OS 백업 | `user.sqlite`와 `-wal`만. Android는 앱 백업이 25MB를 넘으면 클라우드 백업을 하지 않으므로 20MB를 넘으면 설정에 안내. iOS 사이드로드 복원은 미확인. **보장은 자동 백업 파일입니다** |
| 스키마가 더 새로움 | `user.sqlite`의 `user_version`이 앱보다 높으면 열지 않고 앱 갱신을 안내. 파일은 건드리지 않음 |
| 스키마 변경 전 | `VACUUM INTO`로 사본을 남기고 마이그레이션. 캐시 테이블은 마이그레이션하지 않고 다시 만듦 |
| 앱 삭제 | 앱 폴더가 함께 지워짐. 남는 것은 자동 백업 파일뿐 (이 표 첫 행). 재설치 뒤 백업 폴더를 고르면 그 안의 파일로 병합 복원을 먼저 물음 |

### 3.8 user.sqlite 스키마

이 표가 기준입니다. 사용자 기록의 ID는 UUIDv7, 가져온 행은 UUIDv5입니다. 공통 컬럼은 `id`, `created_at`, `updated_at`, `deleted_at`, `device_id`이고, `ride_leg`는 ride에 묶이며 `setting`은 자연키입니다. 시각은 UTC 밀리초입니다.

**원본**

| 테이블 | 주요 컬럼 |
|---|---|
| `trip` | title, note |

### 4.2 ID 동결

**ID 이름** (사용자 결정, 2026-11-03·11-04): 규칙은 DESIGN §2.10 「ID 형식」이 유일한 기준입니다. 요약하면 공개·기록 ID(노드 `n_`, 노선 `l_`, 계통 `r_`, 운행 계통 `s_`, 사업자 `o_`, 역 묶음 `g_`, 환승 묶음 `hub_`, 열람 전용 `a_`)는 접두사 뒤에 영어 이름이고 **숫자·해시·`_b` 금지**(`_b` 같은 이름 아닌 꼬리 금지, 남은 것은 §4.3), 내부 ID(edge `e_`, 승계 사슬 `lg`, carryover `c`)는 사용자 기록에 저장하지 않으므로 번호를 허용합니다. 이름이 겹칠 때 붙이는 순서(회사 → 노선 → `_old` → 지역 이름), 환승 묶음 이름, 지선 계통 이름, 이름 속 숫자도 DESIGN §2.10에 있습니다. ID는 불투명한 값이라 파싱하지 않고, 이름이 바뀌어도 바꾸지 않습니다.

**지금의 ID** (동결 전)

`data/source`는 시드 생성기가 판마다 다시 씁니다. `gen_source.py`는 내부 키를 공개하지 않는 표 `data/imports/id_map.json`(내부 키 → 공개 이름)으로 바꿉니다. 그런데 그 표의 키는 `uid()`가 **선착순**으로 매기는 내부 키입니다 (같은 이름이면 `g_aino_2`, `g_asahi_3`처럼 뒤에 번호). 같은 이름 항목이 앞에 끼면 내부 키가 밀려 공개 ID가 다른 실체에 붙습니다. 생성이 멈추는 것은 표에 없는 키일 때뿐입니다. edge도 일련번호라 역 하나만 끼워도 번호가 밀립니다.

표에 없는 새 항목이 생기면 `gen_source.py`가 멈춥니다. 새 노선을 넣을 때는 `NORIORI_NEW_IDS=1 bash tools/all.sh`로 내부 키를 그대로 낸 뒤 `tools/new_ids.py`가 영어 이름 ID를 표에 더합니다. 겹치면 회사 약칭, 노선 이름 순으로 붙이고, 그래도 겹치면 멈춥니다.

**앱 v1.0 공개 전에는 사용자가 없으므로** 판마다 지문 비교(아래 검사)로 밀림을 잡습니다 (저장소는 2026-11-26에 공개됐지만, 여기서 「공개」는 앱 공개입니다). 앱 공개 뒤에는 기록이 ID를 저장하므로 재생성을 멈춥니다. `id_map.json`은 공개하지 않고, 시드를 동결하면 쓰지 않습니다.

자연키 원장은 만들지 않습니다. 이름과 좌표 격자가 키이면 정정할 때 원장이 다른 역을 같은 역으로 잇거나 같은 역을 끊는데, 그 오류는 조용히 지나갑니다. 재생성 자체를 없애는 쪽이 단순합니다.

**시드 동결** (공개 준비 첫 단계)
1. §4.3의 ID 정리(열람 전용 해시 ID, 환승 묶음 해시 ID, `_b` 꼬리)를 끝냅니다. (2026-11-04 끝남)
2. `gen_source.py`의 마지막 결과를 `data/source`로 확정합니다. 이후 ID는 이 파일에 고정되고 빌드가 새로 매기지 않습니다.
3. `data/overrides`를 `data/source`에 흡수합니다.
4. `gen_source.py`는 이후 `candidates/`에 차이만 제안합니다. `all.sh`는 시드 전용으로 남깁니다. `id_map.json`은 더 쓰지 않습니다.
5. `ids.lock`을 만듭니다. 노드, 노선, 계통, 운행 계통, 사업자, 열람 전용 ID의 추가 전용 목록과 은퇴 목록입니다. 역 묶음, 환승 묶음, 내부 ID는 사용자 기록에 저장하지 않으므로 넣지 않습니다.

**검사**
| 검사 | 내용 |

| 삭제 금지 | 목록의 ID가 사라지면 실패. 은퇴 목록(redirect 또는 묘비 포함)에 있으면 통과 |

### 4.4 CI

워크플로는 여섯입니다 (사용자 결정, 2026-11-04). `CI`가 PR과 main 푸시마다 돌며 `Data`를 한 번 부르고, 그 팩으로 `Flutter`·`Android`·`iOS`를 부릅니다. 넷 모두 PR 체크에 보입니다. `Release`는 태그마다 돕니다.
- 전에는 `Data`가 푸시·PR 양쪽에서 돌고 나머지가 `workflow_run`으로 따라 돌았습니다.
- 그 방식에는 두 문제가 있었습니다. PR 커밋마다 `Data`가 두 번 돌았고, `workflow_run` 실행은 기본 브랜치에 붙어 PR 화면에서 결과를 볼 수 없었습니다.
- 그래서 `CI`가 하위 워크플로를 `workflow_call`로 부르는 방식으로 바꿨습니다.

| 워크플로 | 언제 | 내용 |
|---|---|---|
| `CI` (`ci.yml`) | PR, main 푸시 | `Data` 다음에 `Flutter`·`Android`·`iOS`. 브랜치 푸시는 PR이 있을 때 PR로만 돌아 같은 커밋을 두 번 돌리지 않음. 같은 PR에 새로 올리면 앞 실행은 멈춤. `iOS`는 저장소가 공개라 PR에서도 돎(비공개 저장소였다면 macOS 실행 시간이 10배로 차감되어 main 푸시에서만 돌게 되어 있음). 공개 저장소라 Actions 시간이 들지 않으므로 모든 커밋에서 CI를 돌림(커밋 메시지에 `[skip ci]`를 쓰지 않음, 2026-11-27). 로컬 깨끗한 CI도 푸시 전에 계속 돌림. Actions 탭에서 손으로도 돌릴 수 있음(`workflow_dispatch`) |
| `Data` (`data.yml`) | `CI`·`Release`가 부름 | 개인 정보 검사, 의존 방향(`check_boundaries.py`), 데이터 파이프라인 재생성과 검증(`all.sh`: imports 없이 컴파일 → 글리프·타일 → `verify.py` → `check_geometry.py` → `check_ids.py` → `core_fixture.py`), 앱 시뮬과 불변식(`appsim.py`, `invariants.py`), 팩 생성(`sync_pack.sh`). `build/`와 앱 자산 팩을 3일 보관. 배지 없음 |
| `Flutter` (`flutter.yml`) | `Data` 잡 뒤 (`CI`·`Release`) | 같은 실행의 팩으로 생성 코드 diff(drift, slang), `flutter analyze`, core·store·앱 시험 |
| `Android` (`android.yml`) | `Data` 잡 뒤 (`CI`) | 같은 실행의 팩으로 릴리스 빌드. 디버그 서명 APK를 3일 보관 |
| `iOS` (`ios.yml`) | `Data` 잡 뒤 (`CI`) | 같은 실행의 팩으로 서명 없이 릴리스 빌드. 서명 안 된 IPA를 3일 보관 |
| `Release` (`release.yml`) | `v1.2.3` 태그 | 다음 순서로 돎:<br>1. 먼저 검사한다. 태그와 pubspec 버전이 같은지, 빌드 번호가 앞선 릴리스의 IPA보다 큰지, 직전 태그 뒤 `data/source`·`data/overrides`·`data/sources.json`이 바뀌었는데 `edition`이 그대로가 아닌지.<br>2. `Data`로 팩을 만들고 `Flutter` 시험을 통과한 뒤에만 서명 없는 IPA(`noriori-<버전>-b<빌드>.ipa`)를 GitHub Releases에 올림.<br>3. 모든 릴리스의 IPA로 AltStore·SideStore 소스(`tools/altstore_source.py`, 정보는 `distribution/altstore/meta.json`)를 만들어 그 릴리스에 `altstore.json`으로 붙임.<br>소스 주소는 `releases/latest/download/altstore.json` 하나로 고정 |

README에는 Flutter, Android, iOS 배지가 있습니다(shields.io 아이콘 배지). `flutter.yml`·`android.yml`·`ios.yml`은 `CI`가 부르는 재사용 워크플로라 따로 실행 기록이 없으므로, 배지는 워크플로 상태가 아니라 main 마지막 커밋의 작업 결과(check-runs, 작업 이름 `flutter / flutter` 등)를 읽습니다. 모든 커밋에서 CI를 돌리므로(`[skip ci]` 쓰지 않음) main 마지막 커밋에는 늘 결과가 있습니다. `Data`는 배지 없이 돕니다. 정식 서명 키는 CI에 두지 않습니다 (§4.5).

`verify.py`는 CI에서도 돌지만 station_database 이름 대조는 `data/imports`가 있을 때만 합니다. `audit_ext.py`는 `data/imports`가 필요해 로컬 전용입니다. CI는 네트워크를 쓰지 않습니다.

**판 릴리스 절차** (로컬. 앱 릴리스는 태그를 올리면 `Release`가 IPA와 소스를 올리고, 정식 서명 APK는 로컬에서 만들어 같은 릴리스에 올립니다)
1. 내용이 바뀌면 `data/overrides/as_of.json`의 `edition`을 올립니다 (§4.5). 태그 때 `Release`가 직전 태그와 비교해 다시 확인합니다.
2. `bash tools/all.sh`를 `data/imports`가 있는 상태로 돌립니다. 컴파일 검사 오류, `verify.py`, `check_geometry.py`, `check_ids.py`(ID 잠금, §4.2), `appsim.py` 시나리오 FAIL, `invariants.py` 위반 중 하나라도 있으면 멈춥니다. 마지막에 `tools/audit_db.py`(설계 규칙), `tools/audit_ext.py`(원자료 대조, `data/imports`가 있을 때), `tools/dev/regression/run.py`(전수 대조 1·2회차 지적 회귀 대조)가 돌고 지금은 단계별 건수만 보입니다. `NORIORI_AUDIT_STRICT=1`이면 오류(err) 항목이나 남은 회귀 사례가 있을 때 멈춥니다.
3. 판 사이 재해석 비교(`tools/repro/`가 시작점, 미완), 쿼리 계획 검사(미구현).
4. `bash tools/sync_pack.sh`. `check_edition.py`가 앱 자산의 이전 manifest와 비교해, 내용이 바뀌었는데 판이 같으면 멈춥니다. 이전 팩이 없는 깨끗한 체크아웃(CI)에서는 비교할 대상이 없어 검사하지 않습니다.
5. 태그를 올리면 `Release`가 IPA와 데이터 팩(`noriori-pack-<판>.zip`, `manifest.json`)을 빌드 증명(attestation)과 함께 릴리스에 올립니다. 그 태그를 체크아웃해 `tools/all.sh`를 돌린 이 기기에서 `NORIORI_MANIFEST_KEY=<개인 키 경로> bash tools/release_pack.sh <태그> --upload`가 매니페스트에 서명해 `manifest.json.sig`를 같은 릴리스에 올립니다(§4.5). 정식 APK는 `--into-app`으로 릴리스 팩과 서명을 앱 자산에 넣은 뒤 만듭니다.

### 4.5 배포

데이터 팩은 앱에 포함됩니다. 내려받기(P1)를 위해 같은 파일과 `manifest.json`, `manifest.json.sig`를 GitHub Releases에도 올립니다. 서명은 사람이 오프라인 키로 합니다 (2026-11-28).

- **키**: ed25519 키 두 쌍. 하나를 잃어도 다른 하나로 서명할 수 있습니다. 개인 키는 저장소·CI 밖의 오프라인 보관 장소에만 두고, 공개 키는 `data/keys/manifest-ed25519-1.pub.pem`·`-2.pub.pem`과 앱 상수 `manifestPublicKeys`(`packages/noriori_store/lib/src/pack/pack_signature.dart`)에 같은 값으로 둡니다(`python3 -I tools/sign_manifest.py keys`로 대조).
- **서명**: 팩과 매니페스트는 `Release` 워크플로가 만들고 빌드 증명을 붙여 올립니다. 개인 키는 CI에 두지 않으므로 서명만 로컬에서 붙입니다(`tools/release_pack.sh <태그>` → `tools/release_sign.py`). 서명은 매니페스트에 하고 매니페스트가 파일마다 해시를 적으므로, CI가 만든 팩 전체를 보증합니다. 서명 전에 ① 팩 묶음과 매니페스트의 빌드 증명(`gh attestation verify`), ② 파일마다 해시·크기, ③ 같은 커밋으로 이 기기에서 만든 DB와 표마다 행 내용이 같은지를 확인하고, 하나라도 어긋나면 서명하지 않습니다. CI와 이 기기의 팩은 SQLite·타일 바이트가 달라 파일 해시로는 비교할 수 없지만 내용은 같습니다(2026-11-28 확인). 빌드가 매니페스트를 새로 쓰면 옛 서명은 지워지고, `tools/sync_pack.sh`는 지금 매니페스트와 맞는 서명만 앱 자산에 넣습니다.
- **앱**: 서명 파일이 있으면 공개 키 가운데 하나로 맞아야 그 판을 씁니다. 맞지 않으면 그 판을 쓰지 않습니다(`PackUnavailable`). 서명하지 않은 개발판은 그대로 씁니다.

| 항목 | 내용 |
|---|---|
| `edition` | `YYYY-MM-DD` 또는 같은 날의 고침 판 `YYYY-MM-DD.N` (지금 `2026-11-05.2`). 날짜를 먼저 비교하고, 같으면 N을 수로 비교합니다. N이 없으면 0입니다 (`compareEditions`). 문자열 순서로 비교하지 않습니다 |
| `schema_version` | 정수. 앱은 자기가 지원하는 값과 같은 팩만 씁니다 |
| 최소 앱 버전 | manifest에 둡니다. 미구현 |
| `files` | 파일마다 `sha256`, `size` |
| 필수 파일 | `master.sqlite`(배포판은 `pack-master.sqlite`를 이 이름으로), `names.sqlite`, `rail.pmtiles`, `manifest.json` |
| 선택 파일 | `rail-osm.pmtiles`, `base.pmtiles`, `glyph-*.pbf`. 형식상 선택이지만 배포하는 모든 팩(앱 자산, Releases)에 넣습니다. `rail-osm.pmtiles`가 빠지면 현행 18구간의 선이 사라집니다 |

**앱 서명은 첫 공개 전에 정합니다.** 서명이 다른 APK로 갈아타려면 앱을 지워야 하고, 앱을 지우면 기록이 사라집니다. 앱 ID는 `app.noriori`입니다 (확정).
- 정식 서명 키는 개발자 로컬 보관소에만 두고 CI에 두지 않습니다. CI는 디버그 서명만 합니다.
- GitHub APK와 Play는 같은 키를 씁니다. Play App Signing에 그 키를 등록합니다.
- F-Droid는 재현 빌드로 같은 서명을 유지할 수 있을 때만 올립니다. `maplibre_gl`이 `play-services-location`에 의존하므로 패치도 필요합니다. 안 되면 v1.0 뒤로 미룹니다.

## 5. 서버

**v1.0 범위 밖입니다.** 앱은 끝까지 서버 없이 완성합니다. 그때 쓸 생각은 [server-notes.md](server-notes.md)에 있고, 그 문서는 v1.0의 규범이 아닙니다.

요구사항은 하나입니다. **동기화와 순위 대결을 넣어도 홈 미니PC 한 대로 충분해야 합니다.** 서버는 기기가 암호화한 값을 저장하고 돌려줄 뿐 계산하지 않습니다. 이 맥에서 잰 슬롯 표는 기록 10만 건에 74.1MB, 새 변경 없는 폴링 0.002ms, 올리기 초당 734회입니다 (HTTP 제외).

| 지금 앱에 넣음 | 이유 |
|---|---|
| 사용자 기록 ID를 UUIDv7로 | 기기끼리 충돌 없음 |
| `updated_at`, `deleted_at`, `device_id` | 나중에 병합 기준의 시작값. 복원 병합에 지금도 필요 |
| 변경은 `RecordStore.apply` 한 곳 | 동기화가 끼어들 자리. UI와 다른 계층은 서버를 몰라도 됨 |
| 통계는 순수 함수 | 순위 요약을 그대로 올림 |

그 밖의 HLC, 슬롯, 전송 상태, 계정, 암호화는 만들지 않습니다. 서버 단계의 마이그레이션 한 번으로 추가합니다.

### 7.1 설계 검토를 멈추는 기준

종이 검토는 적대적 검토자에게 물으면 언제나 지적이 나오므로, 지적이 0건이 되는 것을 기준으로 삼지 않습니다. 아래를 만족하면 멈추고 구현합니다.

1. 구조 검토에서 새 테이블이나 새 상태를 요구하는 지적이 없습니다.
2. 불변식마다 실제로 돌아가는 시험이 있습니다.
3. 규칙을 끄면 시험이 실패합니다.
4. 데이터 표본의 오류를 유형별로 전수 집계했고, 체계적 유형이 남지 않았습니다.
5. 규칙으로 고친 결과는 규칙 밖에서 확인했습니다. 같은 규칙으로 다시 세면 놓친 것이 보이지 않고, 시험 통과는 모델에 넣은 시나리오만 보장합니다.

그 뒤의 세부 문제는 문서를 고치지 않고 시험을 더해서 잡습니다. 새 메커니즘을 제안하는 지적은 §0.1의 복잡도 규칙을 통과해야 합니다.
