# 서버 메모 (v1.0 범위 밖, 비규범)

> 서버 단계에 들어갈 때 다시 설계합니다. v1.0을 만들 때 이 문서를 따르지 않습니다. v0.4까지의 검토에서 나온 생각을 잃지 않으려고 남깁니다.
>
> v1.0 앱에는 HLC, 슬롯, `sync_state`가 없습니다. 서버를 붙일 때 `updated_at`과 `deleted_at`을 시작값으로 삼아 마이그레이션 한 번으로 만듭니다. 구간 끄기는 v0.5에서 기록 편집으로 바뀌었으므로 아래의 `ride_exclusion`은 없고, 두 기기가 같은 기록을 동시에 자르면 겹칠 수 있다는 점을 그때 다룹니다. 규칙 모델은 `tools/model_sync.py`입니다.

**지금은 만들지 않습니다.** 앱은 끝까지 서버 없이 완성합니다. 이 장은 나중에 붙일 때 앱 구조를 바꾸지 않기 위한 약속입니다.

### 5.1 책임

| 한다 | 안 한다 |
|---|---|
| 암호화한 슬롯 저장·중계 | 기록 해석, 내용 읽기, 통계 계산 |
| 공개에 동의한 통계 요약 순위표 | 개별 기록 공개, 지도·데이터셋 서빙 |

데이터셋 미러는 정적 파일 서버면 되므로 API에 두지 않습니다. 복구는 새 기기가 슬롯을 모두 받는 것으로 끝나므로 별도 백업 API도 두지 않습니다.

### 5.2 요구사항: 홈 미니PC 한 대

동기화와 순위 대결을 다 넣어도 홈 미니PC 한 대에서 돌아야 합니다. 설계가 이것을 보장하는 이유:

| 설계 | 효과 |
|---|---|
| 서버는 암호문만 저장 | 복호화, 경로 계산, 재해석이 서버에 없음 |
| 기록당 슬롯 고정 | 기록을 고쳐도 저장량이 늘지 않음. 이력을 쌓지 않음 |
| 순위는 기기가 올린 요약 | 서버는 정렬만 함 |
| 변경분 폴링 | 연결을 유지하지 않음. 앱을 열 때, 저장 뒤, 켜 둔 동안 주기적으로 |
| 데이터셋은 정적 파일 | GitHub Releases가 그대로 처리 |
| 프로세스 1개, SQLite 파일 1개 | 운영 대상이 볼륨 하나 |

**실측** (2026-11-01, 이 맥에서 SQLite 직접 호출, 슬롯 표와 인덱스만. HTTP와 TLS 비용은 빠졌고 미니PC 측정이 아닙니다)

| 항목 | 결과 |
|---|---|
| 기록 10만 건 (슬롯 20만 개, 기록 평문 200~560바이트 가정) | 파일 74.1MB |
| 새 변경 없는 폴링 | 0.002ms |
| 변경 50행 받기 | 0.017ms |
| 새 기기가 기록 500건 전부 받기 | 0.4ms |
| 올리기 (회당 슬롯 20개, 회마다 커밋) | 734회/초 |

이 수치로는 병목이 DB가 아니라 회선과 HTTP 쪽입니다. 그래서 서버 하드웨어 사양을 설계 조건으로 두지 않습니다.

**배치**
| 항목 | 방식 |
|---|---|
| 실행 | Docker 이미지 하나, 볼륨 하나 |
| 나와 가족, 친구 | Tailscale. 공유기 포트를 열지 않음 |
| 공개 순위 | 리버스 프록시 + 도메인. TLS는 앞단이 맡음 |
| 서버가 꺼졌을 때 | 앱은 그대로 동작. 켜지면 밀린 슬롯을 주고받음 |
| 서버 디스크를 잃었을 때 | 기기마다 전체 사본이 있음. `server_epoch`가 바뀌면 기기가 전부 다시 올림 (§5.4) |
| 서버 볼륨을 스냅숏으로 되돌릴 때 | 전용 명령을 씀. 이 명령이 `server_epoch`를 새로 만듦. 볼륨을 손으로 되돌리면 기기가 뒤처졌는지 알 수 없음 |

사람이 많아져 SQLite를 넘어서면 저장 계층만 바꿉니다. 프로토콜은 그대로입니다.

### 5.3 스택

Dart `shelf` + SQLite. 서버도 Dart인 이유는 슬롯 타입을 앱과 공유하기 때문입니다. `dart compile exe`로 단일 실행 파일을 만들어 이미지에 넣습니다.

### 5.4 동기화 모델

`oplog`를 쓰지 않습니다. 묶음 스냅숏을 HLC로 덮어쓰는 규칙(§2.8 I)이면 엔티티마다 최신 값만 있으면 됩니다.

| 엔티티 | 슬롯 | 병합 |
|---|---|---|
| `ride` + `ride_leg` | `content`, `delete` | 슬롯별 HLC 승자 |
| `ride_exclusion` | `content` 하나 | ID가 결정적이라 같은 구간은 한 행. 슬롯별 HLC 승자 |
| `visit` (라벨 포함) | `content`, `delete` | 슬롯별 HLC 승자 |
| `trip` | `content`, `delete` | 슬롯별 HLC 승자 |
| `setting` (허용 목록) | `content` | 키별 HLC 승자. `delete` 없음 |
| `photo`, `change_set`, 파생 전부 | 없음 | 동기화 안 함 |

- `setting` 허용 목록은 `basis`, `carryover`, `show_closed`, `show_archive`, `show_branch`, `original_name`입니다. `server`, `dataset_url`, `theme`, `lang`은 기기별입니다.
- HLC는 `(물리 시각, 카운터, device_id)`입니다. 동점이 없습니다.
- 가져온 행의 첫 HLC는 `(0, 0, device_id)`입니다. 두 기기가 같은 파일을 가져와도 사용자가 고친 값을 덮지 않고, 동점도 없습니다.
- **전송 상태는 서버 단계에서 `sync_state(entity, slot, pushed_hlc)`로 더합니다.** 보낼 것은 `pushed_hlc`와 현재 HLC가 다른 행입니다. 응답을 받으면 **보낼 때의 HLC**만 기록합니다. 전송 중에 고친 값이 "보낸 것"으로 표시되지 않습니다. 받은 행은 그 HLC를 `pushed_hlc`로 적어 되돌려 보내지 않습니다.
- **서버가 초기화되면 기기가 알아챕니다.** `/v1/info`가 `server_epoch`를 주고, `sync_state`와 받기 커서 `sync_cursor(server_epoch, account_id, last_seq)`는 이 값에 묶입니다. 값이 다르면 둘 다 비우고 전부 다시 올립니다. 기기의 커서가 서버 최대 순번보다 크면 같은 처리를 합니다. 설정에 `전체 다시 동기화`를 두어 어떤 어긋남이든 사용자가 풀 수 있게 합니다.
- 서버는 `(account_id, entity_key, slot)`마다 HLC가 가장 높은 행만 남깁니다. 내용은 보지 않고 값만 비교합니다. 삭제 슬롯도 남으므로 지운 기록이 되살아나지 않습니다.
- 받은 행은 원본에 병합하고 `change_seq`를 올립니다. 파생은 평소처럼 따라옵니다. 내 판이 모르는 ID면 `unknown_ref`로 두고 갱신을 안내합니다.

| 테이블 | 컬럼 |
|---|---|
| `account` | id, recovery_hash, rejoin_hash, created_at, display_name?, public_stats |
| `device` | id, account_id, token_hash, added_at, revoked_at? |
| `slot` | seq, account_id, entity_key, slot, hlc, ciphertext |
| `public_stat` | account_id, current_km, alltime_km, edition, updated_at |

| 메서드 | 경로 | 내용 |
|---|---|---|
| GET | `/v1/info` | 프로토콜 버전, 최소 앱 버전, `server_epoch` |
| POST | `/v1/accounts` | 초대 코드로 계정과 첫 기기 |
| DELETE | `/v1/accounts/me` | 계정과 슬롯 전부 삭제 |
| POST | `/v1/accounts/recover` | 복구 증명으로 새 기기 토큰. 전 기기를 잃었을 때 |
| POST | `/v1/accounts/rejoin` | 재가입 증명으로 계정 재등록. 기기가 아는 `server_epoch`와 서버 값이 다를 때만 |
| POST | `/v1/devices/pair` | 기존 기기가 만든 1회용 코드로 기기 추가 |
| POST | `/v1/sync/push` | 슬롯 묶음. 같은 내용 재전송은 무해 |
| GET | `/v1/sync/pull?since=` | 서버 순번 뒤의 슬롯 |
| PUT | `/v1/stats/public` | 공개 동의한 요약 |
| GET | `/v1/leaderboard` | 순위표 |

### 5.5 인증과 암호화

- **인증**: 기기별 무작위 토큰. 서버는 해시만 저장합니다.
- **비밀 하나**: 복구 문구 하나에서 HKDF로 `account_id`, 복구 증명, 재가입 증명, 데이터 키, ID 키를 만듭니다. 처음에 복구 문구를 보여 주고 **기기에는 저장하지 않습니다.** 기기는 복구 증명을 뺀 값과 토큰을 저장합니다. 기기 추가는 QR로 넘깁니다.
- **암호화**: 슬롯을 XChaCha20-Poly1305로 암호화하고 `(entity_key, slot, hlc)`를 인증 데이터로 묶습니다. 서버가 슬롯을 바꿔치기하면 복호화가 실패합니다.
- **서버 ID**: 서버에는 엔티티 ID 대신 `HMAC(ID 키, id)`를 보냅니다. 가져온 행의 UUIDv5가 파일 내용을 드러내지 않게 하기 위해서입니다.
- **기기 해제**: 토큰을 폐기합니다. 키를 회전하지 않습니다. 해제된 기기는 복구 증명이 없고 재가입은 서버가 초기화된 때만 되므로, 살아 있는 서버의 슬롯을 받지 못합니다. 키 회전은 복구 문구를 무효로 만들고 새 키 배포 경로가 필요한데, 막는 위협(서버 침해와 기기 유출이 겹칠 때)에 비해 비쌉니다.
- **서버 초기화**: `account_id`가 복구 문구에서 나오므로 기기들이 따로 재가입해도 계정이 갈라지지 않습니다. 해제 목록은 서버와 함께 사라지므로 초기화 직후에는 해제된 기기도 재가입할 수 있습니다. 홈 서버 규모에서 받아들입니다.
- **유출이 의심되면**: 새 복구 문구로 새 계정을 만들어 전부 다시 올립니다.
- **키 분실**: 복구 문구를 잃어도 기기가 남아 있으면 그대로 씁니다. 기기까지 모두 잃으면 서버 데이터는 못 씁니다.

### 5.6 순위 대결

기기가 `Scorer`로 계산한 `(현행 km, 역대 km, 판 번호)`를 공개에 동의한 사용자만 올립니다. **자기 신고입니다.** 서버가 기록을 읽지 못하므로 값을 검증할 수 없고, 지인 사이의 대결을 전제로 합니다. 판이 다르면 분모가 다를 수 있어 판 번호를 함께 표시합니다.

### 5.7 지금 준비할 것과 안 할 것

| 지금 앱에 넣음 | 이유 |

| 사용자 기록 ID를 UUIDv7로 | 기기끼리 충돌 없음 |

| `device_id`, `install_id`, `hlc_last` | OS 복원 처리와 시계 순서에 지금도 필요 |

| 데이터셋 주소 설정 | 미러 |
| `SyncPort` 인터페이스와 빈 구현 | UI와 store가 서버를 몰라도 됨 |

| 지금 안 만듦 | 언제 |
|---|---|
| `server/`, `noriori_protocol`, `noriori_sync` | 서버 단계 |
| 계정, 로그인, 암호화 코드 | 서버 단계 |
| `sync_state` 테이블 | 서버 단계의 마이그레이션 1회 |

| 사진 동기화 | 첫 서버 범위 밖 |
